# Spec: 周报默认本周 + 当前周锐评支持刷新

> 术语见后端 `CONTEXT.md`（周报锐评），决策依据：`docs/adr/0007`（历史周不可变）。
> 本次决策将新增 ADR 0010 记录。

## Problem Statement

车队成员打开周报页时，默认展示的是**上一个自然周**的报告——但成员更关心"本周打到
现在打得怎么样"，还要手动点一次"下周"才能看到本周，操作多余且容易误以为数据没更新。

另外，当前周（进行中）的 AI 锐评有 10 分钟短缓存，缓存期内新入库的对局不会反映到
锐评里，且页面上没有任何办法主动刷新——用户只能干等缓存过期。

## Solution

1. **默认周期改为本周**：前后端同步把周报的默认锚点从"今天减 7 天"改为"今天"。
   不传 `date` 参数时，周报统计与锐评都默认落在本周（今天所在的自然周，
   周一~周日，东八区口径不变）。

2. **当前周锐评支持强制刷新**：锐评 SSE 接口新增可选参数 `force`，为 true 时跳过
   内存短缓存、重新调用 AI 流式生成。历史周保持 ADR 0007 的"落库不可变"设计
   不变：force 对历史周被忽略（返回存档文本），不做重新生成。
   服务端对同周强制刷新有 60 秒冷却，防止误触/恶意无限消耗 AI token。

## User Stories

1. 作为车队成员，打开周报页时默认看到的就是本周（今天所在自然周）的周报，无需手动切换。
2. 作为车队成员，在历史周与本周之间切换后回到"本周"，页面仍正确落在今天所在的周。
3. 作为车队成员，直接调用周报接口不传 date 时，得到的是本周的数据（前后端口径一致）。
4. 作为车队成员，本周有新对局入库后，我可以点击锐评区域的刷新按钮，立即重新生成锐评，而不必等待 10 分钟缓存过期。
5. 作为车队成员，点击刷新后，旧锐评文本被清空，新锐评以打字机效果重新流式输出。
6. 作为车队成员，流式生成进行中时刷新按钮置灰，我无法重复点击触发并发请求。
7. 作为车队成员，查看历史周锐评时看不到刷新按钮（锐评已归档、内容不可变），不会产生"点了没反应"的困惑。
8. 作为车队成员，在 60 秒冷却期内点击刷新时，服务端直接返回缓存内容，页面仍能正常展示锐评。
9. 作为 API 调用方，我对历史周传 force=true 时不会报错，而是正常收到存档文本（宽容语义）。
10. 作为维护者，历史周的锐评仍然只调用一次 AI，既有成本控制（ADR 0007）不被破坏。
11. 作为维护者，我能从日志区分三种刷新路径：正常缓存命中、强制刷新重新生成、冷却期内拦截，便于排查与成本审计。
12. 作为维护者，强制刷新接口有服务端 60 秒冷却兜底，即使绕过前端直接调 API 也无法无限消耗 AI token。
13. 作为开发者，本次决策（默认本周、当前周可刷新）有 ADR 记录，词汇表中"周报锐评"词条反映最新的刷新语义。

## Implementation Decisions

- **默认锚点改为今天**：后端周报聚合服务在 date 缺省时不再减 7 天，直接取今天；
  前端周报页的默认周锚点函数同步改为今天。周界折算逻辑（自然周、周一~周日、
  东八区）完全不动，只改默认值。
- **force 参数挂在现有 SSE 接口上**：锐评 SSE 接口新增可选布尔参数 `force`，
  不新增独立刷新端点——一次请求完成"失效缓存 + 重新流式生成"。
- **force 只对当前周生效**：当前周 = 周结束时间戳大于当前时间。历史周收到
  force=true 时忽略该参数，照常走持久化命中路径返回存档文本，并记日志。
- **60 秒冷却**：服务端对同一周的强制刷新记录时间戳，冷却期内再次 force 请求
  不调 AI，直接返回缓存内容（并记日志）。冷却计时与内存短缓存相互独立。
- **前端刷新按钮**：锐评卡片上加刷新按钮；流式生成中置灰不可点；点击后绕过
  composable 的同周去重逻辑（刷新是显式意图，不等于重复请求），清空旧文本、
  带 force=true 重新发起流式。
- **历史周隐藏按钮**：前端根据周结束时间与当前时间比较判断"当前周"，历史周
  不渲染刷新按钮。
- **路由层约定**：controller 只做参数校验与 SSE 装配，force/冷却/缓存失效逻辑
  下沉 service 层，沿用项目分层约定。
- **文档**：新增 ADR 记录两个决策（默认本周、当前周可刷新 + 60 秒冷却 +
  历史周 force 忽略）；同步修订后端 `CONTEXT.md` 的"周报锐评"词条。
  不改动 ADR 0007 原文。
- **日志**：关键节点必须打日志——force 被忽略（历史周）、冷却期内拦截、
  强制刷新重新生成。

## Testing Decisions

- 好的测试只测外部行为：SSE 事件序列、AI 是否被调用、参数透传、按钮显隐，
  不测私有方法与内部数据结构。
- **后端 service 单测**（`WeeklyAiCommentServiceTest`，mock AiClient）：
  - 当前周 force=true：AiClient 被重新调用（缓存被绕过），完整 SSE 序列正常。
  - 当前周 force=true 后 60 秒内再次 force：AiClient 不被调用，返回缓存内容。
  - 冷却过期后再次 force：AiClient 再次被调用。
  - 历史周 force=true：走持久化命中路径，AiClient 不被调用。
  - 普通请求（无 force）行为与现状完全一致（回归保护）。
- **后端默认周期测试**（`WeeklyReportServiceTest`）：date 缺省时落在今天所在周。
- **后端 HTTP 层装配**（`TeamControllerIntegrationTest`）：force 参数可正确
  透传到 service 层。
- **前端 API 测试**（`team.test.ts` 先例）：流式请求正确携带 force 参数。
- **前端 composable 测试**（`useWeeklyComment`）：刷新调用绕过同周去重、
  生成中状态正确。
- **前端组件测试**（`WeeklyView`）：当前周显示刷新按钮、生成中置灰、
  历史周隐藏按钮。
- 测试路径与被测文件保持一致，遵循 TDD 红绿灯（先红后绿）。

## Out of Scope

- 历史周锐评的重新生成/覆盖（维持 ADR 0007 不可变设计）。
- 周界计算逻辑、周报统计口径、七榜单引擎的任何变更。
- QQ 推送周报内容的联动调整。
- 单局 AI 分析等其他 AI 场景的缓存策略改动。
- 桌面端（LeagueAkari）的任何改动。

## Further Notes

- 强制刷新 = 真实调用一次 AI 网关（token 成本），60 秒冷却是成本兜底，数值
  可在实现时做成常量（不引入配置项，避免过度设计）。
- 前端"当前周"判断依赖周报响应中的周结束时间戳，与后端判定口径一致
  （同一份周界折算结果），不新造第二套判断。
