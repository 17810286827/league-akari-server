# Spec: 对局诊断区块——闲置 stats 字段的结果归因

> 五项数据价值深挖计划第 ③ 项（增量迭代）。术语见后端 `CONTEXT.md`（对局诊断）。

## Problem Statement

车队成员想知道"这局为什么输"，但现有展示回答不了：战报图只有输出占比/承伤占比/
伤害转化三个指标，OP Score 评分只用 8 个维度，而 `stats_json` 全量快照中大量字段
（视野得分、控制时长、经济分配、资源控制等）完全闲置。败局的短板维度没有直观呈现。

## Solution

对局详情页新增纯数据"诊断"区块：用闲置 stats 字段计算诊断维度（视野得分、控制
贡献、经济分配、资源控制等），每维度展示本人值、队内位次与基线对比；败局自动
高亮短板维度（如"视野得分全队倒数"）。不依赖 AI，与时间线复盘互补（复盘看过程，
诊断看结果归因）。

## User Stories

1. 作为车队成员，打开败局的详情页，诊断区块自动高亮我这局的短板维度，一眼看到"输在哪"。
2. 作为车队成员，每个诊断维度都能看到我的原始值、队内 5 人位次、以及与同英雄基线（scoring_baseline）的对比。
3. 作为车队成员，胜局的详情页也有诊断区块（不高亮短板，展示正常维度表现）。
4. 作为车队成员，诊断维度不与战报图既有三指标（输出/承伤/伤害转化）重复。
5. 作为车队成员，我玩辅助时诊断能体现视野/控制贡献，不会因为伤害低被判为"全面垫底"（职业差异化）。
6. 作为车队成员，队友的数据在诊断区块中也能查看（车队视角，不局限于 self 视角）。
7. 作为开发者，诊断计算不混入 OP Score 评分体系（评分版本已冻结在 v4）。
8. 作为维护者，诊断维度清单可以后续扩充而不改动接口契约（维度列表可扩展设计）。
9. 作为维护者，诊断区块加载不依赖 AI 可用性，纯数据秒出。

## Implementation Decisions

- **纯计算服务**：新增诊断计算服务，输入经既有 `ParticipantStatsReader` 门面读取
  stats_json（统计读取口径已归一，不新开解析路径），输出维度列表（原始值 + 队内
  位次 + 基线偏差 + 短板标记）。
- **维度范围**：必须超出战报图三指标，候选包括视野得分、控制时长、经济分配
  （团队经济占比）、资源控制等；**最终维度清单为待细化项**，实现时从 stats_json
  实际可用字段确定。
- **基线对比**：复用 `scoring_baseline`（全库同英雄每分钟基线），展示本人与同英雄
  平均水平的偏差。
- **短板判定规则**：**待细化**——初步方向为"败局中该维度队内位次末位且低于同英雄
  基线一定阈值"的组合条件。
- **职业差异化**：诊断维度的展示与短板判定考虑英雄职业（辅助的视野/控制权重高）。
- **不进评分**：诊断维度与 OP Score 评分体系完全隔离。
- **不进 QQ 推送**：纯 Web 展示。
- **路由层约定**：controller 参数校验 + 返回封装，计算逻辑在 service 层。

## Testing Decisions

- 好的测试只测外部行为：给定参与者 stats 断言诊断维度输出（值/位次/短板标记），
  不测私有方法。
- **service 层纯计算单测**：先例为评分引擎维度计算测试（OpScoreEngine 系）。
- **读取口径测试**：经 ParticipantStatsReader 的输入不再单独解析 stats_json。
- **职业差异化测试**：辅助职业的视野维度不因伤害低被误判短板。
- **契约测试**：维度列表可扩展——新增维度不改已有字段结构。
- 测试路径与被测文件保持一致，遵循 TDD 红绿灯。

## Out of Scope

- AI 驱动的诊断叙述（与复盘 AI 叙述是两件事）。
- 周报聚合的"本周车队通病"（如"本周 60% 败局视野崩盘"）——后续迭代。
- OP Score 评分体系的任何改动。
- 时间线层面的过程分析（归复盘系统）。

## Further Notes

- 与时间线复盘系统（第 ② 项）在对局详情页**各自独立**：诊断看结果归因，复盘看
  过程曲线，不合并为同一 tab。
- stats_json 的全量字段清单是本 spec 实现前的第一件事（待细化项的事实基础）。
