## Problem Statement

前端对接这个后端时，每个接口的响应形状都不一样：同一个项目里并存四种成功形状（`{code:0}`、`{code:0,data}`、`{data}`、DTO 直出），没有统一返回类型，前端每接一个新接口都要问一次"这次返回什么形状"，拦截器逻辑无法一处写完。

错误语义寄生在 JDK 异常类型上（IllegalArgumentException→400、IllegalStateException→503），错误码就是 HTTP 状态码：既表达不了"是参数错了还是名单没配置还是 Riot 挂了"这类业务错误类别，还存在误分类风险——库深层冒出的 JDK 异常会被统一翻译成"调用方参数错误"，状态码撒谎，排查方向被误导。

公共横切设施散落在业务包里：统计读取门面（stats_json 解析口径的唯一实现）寄居在对局包，被三个兄弟业务包反向 import；异常类分散在各自业务包；util 与 config 两个"公共区"职责含混。此外契约文档与代码漂移（文档仍描述已清空的 service 包、过时的迁移清单），接手者会被误导。

## Solution

建立三件套：**统一响应对象**（`{code, message, data}`，所有 JSON 端点同形，HTTP 一律 200，错误语义全靠业务码）、**全局错误码枚举**（分段数字码，全项目错误唯一登记处）、**业务异常 BizException**（携带错误码，service 直接抛，全局异常处理器统一翻译）。同时把横切设施收拢到公共包（web / exception / stats 三个子包），并同步重写过期的契约文档。

经调研确认的做法依据：错误码"接口 + 枚举"与"全局异常 + 统一响应"是中文 Spring Boot 生态事实标准（mall 系三层模式、阿里《Java 开发手册》错误码章节）；本项目按用户决策采用**无接口的全局单枚举** + **HTTP 状态放弃语义（全 200）**，代价（devtools 全绿、监控无法按 5xx 聚合）已明确接受。

## User Stories

1. As a 前端开发者, I want 所有 JSON 接口返回统一的 `{code, message, data}` 形状, so that 响应拦截器一处写完，不再逐接口记忆响应形状
2. As a 前端开发者, I want 通过业务码精确识别失败类别（参数/车队配置/对局/账号/外部依赖/系统）, so that 能给用户精确提示而不是笼统的"请求失败"
3. As a 前端开发者, I want 判失败只有一条规则（code !== 0）, so that 不需要同时判断 HTTP 状态码和 data 是否存在
4. As a 前端开发者, I want data 字段有值才出现在响应里, so that 同步写接口的响应载荷最小且形状可预期
5. As a 前端开发者, I want AI 分析接口在开流前的失败（Key 未配置、对局不存在）返回带错误码的 JSON, so that 能区分"流还没开就失败"和"流中途失败"
6. As a 后端开发者, I want 业务规则失败时 service 直接抛带错误码的业务异常, so that 失败的表达一处定义、处处引用，不再借 JDK 异常类型当语义通道
7. As a 后端开发者, I want 新增错误必须先在全局错误枚举登记, so that 全项目错误面一眼看全，不存在匿名的失败
8. As a 后端开发者, I want 未识别的 JDK 异常统一落入系统兜底错误码, so that 库深层异常不再被误判成调用方参数错误，排查方向不被误导
9. As a 后端开发者, I want 异常类全部集中在一个公共包, so that 看全项目异常只去一个地方
10. As a 后端开发者, I want 统计读取门面迁出对局包进入公共包, so that 兄弟业务包不再因公共门面反向依赖对局包
11. As a 排查问题的人, I want 错误码分段可读（1xxx 请求参数 / 2xxx 对局 / 4xxx 外部依赖 / 5xxx 系统）, so that 看到 code 就知道去哪一层查
12. As a 排查问题的人, I want 兜底异常保留完整堆栈日志、响应只透出统一文案, so that 系统 bug 可追溯又不泄露内部细节
13. As a 后端开发者（TDD）, I want 契约变更先红后绿——handler 测试与 controller 契约测试先行, so that 改造全程有安全网
14. As a 维护者, I want AGENTS.md 的响应契约与包结构章节随本次改造重写（含迁移清单、service 包描述的更新）, so that 下一个接手者或 agent 会话不被过期描述误导
15. As a 维护者, I want 集成测试断言随契约更新（HTTP 200 + 业务码）, so that 测试始终描述真实契约而非历史契约
16. As a 维护者, I want SSE 事件流与健康检查端点被明确豁免并记录在案, so that 后续不会被误当成"漏改"的端点

## Implementation Decisions

- **统一响应对象**：`ApiResult<T>` 三字段 `{code, message, data}`；成功 code=0、message 固定 "ok"；data 有值才序列化（NON_NULL 策略，同步写接口成功时 data 缺省）；所有 JSON 端点同形，根路径引导信息也归入 data。线上形状（会话中定稿）：

  ```json
  { "code": 0, "message": "ok", "data": { ... } }
  { "code": 0, "message": "ok", "data": null → 缺省 }
  { "code": 2001, "message": "对局不存在: gameId=123" }
  ```

- **HTTP 状态一律 200**，前端双层判别式：HTTP 非 200 = 请求未达业务（路由/容器级故障，如打错路径的 404、方法不支持的 405）；HTTP 200 + code !== 0 = 业务失败。
- **全局错误码**：单一全局枚举（不做接口抽象——用户决策），分段数字码：`0` 成功；`1xxx` 请求与参数（1001 校验失败、1002 gameId 不一致、1003 召唤师名格式）；`11xx` 车队配置（1101 名单未配置、1102 成员解析失败、1103 非车队成员、1104 未知榜单维度）；`2xxx` 对局域（2001 对局不存在、2002 时间线不存在）；`3xxx` 账号域（3001 召唤师不存在）；`4xxx` 外部依赖（4001/4002 Riot、4101/4102 AI）；`5xxx` 系统（5000 兜底、5001 数据组装失败）。码表具体值以实现时的枚举登记为准，段位规则写入枚举类注释。
- **BizException**（命名描述"失败的性质"，与 RuoYi 的 ServiceException、mall 的 ApiException 同位；可换名不影响设计）：RuntimeException 携带全局错误码枚举，支持动态文案覆盖（如 "对局不存在: gameId=123"）。
- **异常三规则**：① 业务规则不满足 → service 直接抛 BizException，不 catch；② catch 仅允许出现在**异常翻译边界**（Riot 统一出口把 404/429 翻译为业务异常——该出口已有此结构，仅换异常类型）；③ 全局处理器统一翻译为统一响应。
- **退役清单**：IllegalArgumentException→400、IllegalStateException→503 两条 JDK 语义通道（未识别 JDK 异常落 5000 兜底）；对局不存在、召唤师不存在两个独立异常类（被 BizException + 错误码吸收）；全局处理器中的 ResponseEntity 状态语义。
- **公共包抽离**（用户决策：异常是公共物，即使模块特有也集中放置；包注释记录"异常跟域走是特性分包终局，规模变大后可按域拆回"）：
  - `common/web`：统一响应对象、全局异常处理器（自 config 包迁入）、客户端断连识别工具（自 util 迁入，util 包随之删除）；
  - `common/exception`：全局错误码枚举、BizException、QQ 推送异常（自 qqbot 包迁入——它不进 HTTP 边界，驱动播报状态机，保留为独立技术异常）；
  - `common/stats`：统计读取门面（自 match 包迁入，解除 scoring/team/broadcast 对 match 包的门面级反向依赖）。
- **不迁移**：Riot/AI/QQ 客户端与游戏数据服务（领域 SDK 而非横切设施）、提示词加载器（单一家族工具）、分页响应 DTO（随 dto 归位票决策）。
- **豁免清单**：AI 分析 SSE 事件流（协议自成契约；注意其开流前失败改为 HTTP 200 + JSON 错误体，前端该接口需能处理"等到 JSON 而非流"）、健康检查端点（Spring 管理）。
- **改造范围**：约 20+ 个抛出点迁移、全局处理器重写、约 5 个 controller 集成测试断言更新、全部 service 测试中 JDK 异常断言改为 BizException+错误码断言。
- **文档同步**：AGENTS.md 重写响应契约章节、包结构描述、迁移清单（V1–V7）；交接文档的异常映射表同步更新；Q2 三项（controller 播报编排下沉、dto 归位、聚合服务拆分）另行开票。
- **提交风格**：Conventional Commits 中文描述，按步骤拆分提交（契约与异常基建 / 抛出点迁移 / 包抽离 / 文档同步）。

## Testing Decisions

- **好测试的标准**：只断言外部可见行为——线上 JSON 形状、业务码值、HTTP 200——不断言实现细节（内部方法调用、私有结构）。
- **测试接缝（全部为现有接缝，不新增；会话中已确认）**：
  1. **HTTP 边界（最高接缝）**：MockMvc 打控制器，断言统一响应契约与错误码。既有先例：对局控制器集成测试、车队控制器集成测试、播报集成测试。
  2. **全局处理器单元接缝**：BizException→统一响应映射、校验失败→参数错误码、兜底→系统错误码。既有先例：全局异常处理器测试。
  3. **service 单元接缝**：业务规则断言保持不变，异常断言从 JDK 异常类型改为 BizException + 错误码。既有先例：各业务包现有单测（评分引擎、对局摄取、车队统计等约 40 个测试类）。
- **TDD 顺序**：第一批红测试 = 全局处理器映射测试 + controller 契约新形状断言；实现后转绿；抛出点迁移与包抽离每步保持全量测试通过。
- 测试路径与被测路径镜像的仓库约定继续维持（公共包测试放公共包镜像路径）。

## Out of Scope

- 三项结构收敛（本会话 Q2 挂起项，另行开票）：MatchController 中的播报编排下沉或事件化、dto 按特性归位、车队聚合服务按查询场景拆分。
- 前端/桌面端适配（独立仓库；本 spec 落地后前端需同步：拦截器改判 code、AI 分析接口处理 JSON 形态的开流前失败）。
- 错误码的接口化/多枚举扩展机制（单枚举对当前规模足够，域级拆分将来另议）。
- 恢复 HTTP 状态语义、监控按 5xx 聚合（已决定放弃 HTTP 状态语义，代价已接受）。
- 任何业务逻辑变更（本 spec 纯基础设施与契约改造，不触碰评分、播报、车队统计的口径）。

## Further Notes

- 调研依据（会话中完成）：mall 系 IErrorCode/ApiException 三层模式、阿里《Java 开发手册》A/B/C 五位错误码规范、Baeldung/Spring 官方异常处理实践；本项目偏离处（无接口单枚举、HTTP 全 200）均为用户明确决策。
- AGENTS.md 用户级规则"service 层抛出异常、路由层统一捕获异常"与本 spec 一致；本次改造是把这条规则的"异常"升级为带业务码的类型化通道。
- 前端拦截器契约一句话：`HTTP 非 200 → 网络/路由问题；HTTP 200 && code !== 0 → 业务失败（message 直接可展示）；否则 res.data 即业务数据`。
