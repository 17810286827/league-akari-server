# 0007. 周报 AI 锐评独立 SSE 流式 + 历史周持久化

- 状态：已采纳（accepted）
- 日期：2026-09-05
- 关联：[0005-ai-client-unified-invocation](./0005-ai-client-unified-invocation.md)（AI 客户端统一调用，本决策复用其流式管道）

## 背景与问题

`GET /api/team/weekly` 一次性返回整份周报（总览 + 七榜单 + 名场面 + AI 锐评），
AI 生成耗时导致整个请求被拖慢，用户体验差。且周报在每次访问时重新调用 AI，
同一周反复访问既重复花钱又重复等待。

## 决策

1. **统计数据与 AI 锐评拆分**：统计数据照旧同步返回（本来就快），
   新增独立 SSE 接口（如 `GET /api/team/weekly/ai-stream`）流式输出 AI 锐评，
   Web 端周报页先渲染榜单/名场面，锐评以打字机效果逐字出现。
   事件契约（start/chunk/reasoning/done/error）复用单局分析 SSE 的既有约定。
2. **历史周锐评持久化**：已结束的周内容不可变——首次流式生成完成后将完整
   锐评文本落库（新增 `weekly_report_ai` 表），后续请求直接同步返回，不再调 AI；
   当前周（进行中）用短缓存，因为新对局会改变内容。

## Considered Options

- **整份周报全部走流式** → 否决——统计数据本身生成很快，没有流式必要，
  反而把简单的同步接口复杂化
- **与单局分析一致的短时缓存** → 否决——过去的周是天然不可变数据，
  短缓存意味着同一份内容过期后重复调用 AI，成本与延迟双输

## Consequences

- 单局分析与周报锐评的缓存策略从此不一致（前者 2 分钟缓存、后者历史周永久落库），
  这是有意为之：单局对局详情页可能因时间线补同步而变化，周报的过去周不会
- 当前周的"短缓存"具体时长实现时定，需与对局同步频率（2 分钟轮询）协调
