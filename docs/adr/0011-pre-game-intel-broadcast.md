# 0011. 敌方情报推送：桌面端 SGP 喂数据 + 后端计算 + 游戏开始触发推送

- 状态：已采纳（accepted）
- 日期：2026-09-06
- 关联：[0003-qq-official-bot-push](./0003-qq-official-bot-push.md)（车队群推送通道与"失败不静默"原则）、
  [0008-timeline-replay-rules-plus-ai](./0008-timeline-replay-rules-plus-ai.md)（"规则可测、AI 不编造"哲学）

## 背景与问题

需求：车队进入对局选人阶段时，自动向车队 QQ 群推送敌方情报——我方红蓝方归属、
敌方是否有开黑队伍、开黑组合与各玩家胜率、段位。

关键事实约束（2026-09-06 代码调查）：

1. **"进房间"不可行，"进选人"才可行**：组队大厅（lobby）阶段客户端拿不到敌方 5 人
   与红蓝方分配；数据最早可得时机是 champ-select 开始（teamId 100/200、双方 puuid 就绪）。
2. **选人窗口只有 30-60 秒**，而敌方开黑判定需要 5 人 × ~20 局历史对局。
3. **后端 Riot API 拉陌生敌方历史不可行**：MATCH-V5 走 90 次/120 秒限流，
   100 局请求至少 2-3 分钟，选人早结束。桌面端走 SGP 通道（登录态、近乎无频控），
   这是它选人阶段几十秒内拉完 10 人历史的根本原因。
4. 桌面端 `ongoing-game` 已有开黑推断（共现 + 阈值 + 子集剔除 + 重叠合并）与
   个人/团队胜率分析（TS 实现）；后端riot 包只有面向车队成员的回填能力。

## 决策

1. **分工 = 桌面端搬数据、后端算、后端推**：桌面端在选人阶段新增"敌方侦察上报"
   推送器（仿 match-sync 现有 HTTP POST + 重试模式），把 SGP 拉到的敌方 match 摘要
   （每局 participants：puuid/teamId/胜负/召唤师名 + queueId）与敌方段位喂给后端；
   后端收到后自行计算开黑判定、窗口胜率，渲染情报卡并推送。计算逻辑集中 Java
   服务端（可复用、可测试、Web 端未来也能展示），数据搬运借用 SGP 快速通道。

2. **推送时机 = 游戏真正开始（Gameflow InProgress），一局只推一条**：
   等分析完整再推（而非进选人就推半截）；以游戏开始为触发与去重锚点，
   选人秒退/秒锁退的对局自然不推。桌面端在选人阶段尽力喂数据，
   游戏开始时发"开始信号"，后端以开始信号为发卡触发点。

3. **超时降级，不静默**：后端在截止时刻用手头已有数据出卡，缺谁的 History
   就在卡上如实标注"数据未知"，开黑判定按可得数据计算。延续 ADR 0003
   "群里永远有交代"的失败语义。

4. **开黑判定口径 = 桌面端同口径移植**：共现 ≥ 阈值（`premade-detection` 配置项）
   + 子集剔除 + 重叠合并，Java 版移植 `team-up-calc` 逻辑。不在判定阶段引入
   胜率权重——组合胜率是卡上的展示信息，不是判据。

5. **胜率口径 = 20 局窗口原始胜率**：胜场/局数，不做队列过滤，零额外请求；
   局数一并展示（小样本不裸百分比，对齐搭档胜率矩阵原则）。

6. **我方锚定 = roster 多数派**：按成员身份集合匹配选人数据，车队成员多数所在队
   为我方（复用车队对局主队判定语义）；上报者身份仅参考。

7. **消息形态 = 敌方情报卡 PNG（复用战报图管线）**：Java2D 渲染 900px 卡片，
   内容为标题（车队 + 红蓝方 + 队列）+ 敌方 5 人行（名/段位/窗口胜率）+ 开黑分组
   + 各组搭档胜率。不包含我方 5 人。富媒体上传 + msg_type=7 推送，纯数据不依赖 AI。
   队列范围不设白名单，所有 5v5 选人队列都推。

8. **敌方侦察数据轻量落库作缓存**：只存共现判定所需摘要行（对局 ID、玩家 puuid、
   teamId、胜负），不落详情；再遇同一批人时命中缓存，减少桌面端喂数据量。
   量级：一次选人约 1000 行，无压力。

## Considered Options

- **进选人立刻推基础信息 + 分析完补推第二条** → 否决：一局两条刷屏，情报感割裂
- **后端自己调 Riot API 拉敌方历史** → 否决：限流下 2-3 分钟起步，选人窗口等不起；
  等于在 Java 里重写桌面端全套选人分析且数据还更慢
- **桌面端算完把结果推给后端转发** → 否决：计算逻辑散落两端，后端沦为哑管道，
  Web 端无法复用，口径漂移无单点治理（战报图 0:0 bug 的教训）
- **分析不完整就不推** → 否决：某些局完全静默，违背"群里永远有交代"原则
- **开黑判定加胜率权重（有化学反应才算威胁）** → 否决：样本小时易误判，且与
  桌面端 UI 口径分叉
- **双列卡（我方 vs 敌方）** → 否决：我方信息群友自见，卡上纯冗余，布局复杂度翻倍
- **只推排位队列** → 否决：情报卡在匹配/大乱斗同样有"敌方是谁"的围观价值，
  白名单是多余的门禁

## Consequences

- 桌面端 LeagueAkari 新增一个 shard 级推送器（选人阶段喂数据 + 游戏开始信号），
  依赖后端可达；后端不可达时的丢数据由"下次命中不了缓存"承担，不影响本局降级出卡
- 后端新增：选人侦察接收接口、开黑判定引擎（Java 版 team-up-calc，含单测）、
  敌方情报卡渲染布局（复用战报图组件与中文字体）、侦察缓存表（Flyway 迁移）
- 红蓝方语义依赖 teamId 常量（100 蓝 / 200 红），沿客户端惯例，需在渲染层做映射注释
- 陌生人（非车队成员）对局摘要行入库，属客户端公开可见数据，敏感度低；
  若未来有合规顾虑，可按"仅保留最近 N 次选人"做滚动清理，不改变本决策
- 术语：敌方情报推送、敌方情报卡、敌方侦察数据、开黑判定口径、窗口胜率、我方锚定
  见 `CONTEXT.md`
