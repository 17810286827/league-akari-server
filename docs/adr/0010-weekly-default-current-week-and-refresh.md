# 0010. 周报默认本周 + 当前周锐评支持强制刷新

- 状态：已采纳（accepted）
- 日期：2026-09-06
- 关联：[0007-weekly-ai-stream-and-persistence](./0007-weekly-ai-stream-and-persistence.md)（历史周不可变持久化，本决策保持不变）

## 背景与问题

周报默认展示"上一个自然周"——但成员更关心"本周打到现在打得怎么样"，
打开页面还要手动点一次"下周"，操作多余且容易误以为数据没更新。

另外，当前周（进行中）的 AI 锐评有 10 分钟 JVM 短缓存，缓存期内新入库的对局
不会反映到锐评里，页面上也没有任何主动刷新手段，用户只能干等缓存过期。

## 决策

1. **默认周期改为本周**：前后端同步把周报的默认锚点从"今天减 7 天"改为
   "今天"。不传 `date` 参数时，周报统计与锐评都默认落在本周（今天所在的
   自然周，周一~周日，东八区口径不变）。周界折算逻辑完全不动，只改默认值。
2. **当前周锐评支持强制刷新**：锐评 SSE 接口新增可选布尔参数 `force`，
   为 true 时跳过 10 分钟内存短缓存、重新流式生成。
   - **仅当前周生效**：历史周保持 0007 的"落库不可变"设计——force 对历史周
     被忽略，照常返回存档文本（宽容语义，不报错），并记日志。
   - **60 秒冷却**：服务端对同周强制刷新记录时间戳，冷却期内再次 force 请求
     不调 AI，直接返回缓存内容。冷却计时与内存短缓存相互独立。
3. **前端交互**：锐评卡片加刷新按钮；流式生成中置灰；历史周隐藏按钮
   （按周结束时间与当前时间比较判断"当前周"）。

## Considered Options

- **历史周也支持 force 重新生成（覆盖存档）** → 否决——推翻 0007 的不可变
  设计，历史周"只调一次 AI"的成本保障不复存在，收益却很小（过去的周数据
  不会变，重新生成的锐评内容近似）
- **独立刷新端点（先清缓存再拉流）** → 否决——多一次往返，两个接口状态
  有时序耦合；force 参数挂在现有 SSE 接口上一次请求完成，语义更集中
- **不做服务端限频，只靠前端按钮置灰** → 否决——force 参数裸露在 GET
  上，绕过前端即可无限消耗 AI token；60 秒冷却是成本兜底
- **10 分钟冷却（对齐缓存 TTL）** → 否决——刷新本就是"我现在就想看新内容"，
  10 分钟等于没刷新；60 秒在防滥用与体验间取平衡

## Consequences

- 默认周期的 API 语义变化：不传 `date` 的调用方从"上周"变为"本周"——
  本项目调用方只有 Web 前端（同步改），无外部契约负担
- 历史周 force=true 静默忽略（不报错）：宽容语义，前端已隐藏按钮，
  误调不致弹错；日志留痕便于审计
- 冷却期内的 force 请求返回缓存内容：用户在 60 秒内二次刷新看到的仍是
  旧锐评，属预期行为（前端按钮仅生成中置灰，不做冷却倒计时）
- 冷却时长为常量（不引入配置项），与 10 分钟缓存 TTL 一致避免过度设计
